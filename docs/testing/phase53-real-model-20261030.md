### A：当前存在「TLB = 页表」误区 — PASS

回答直接指出：

判定：**PASS**。

### B：纠正后的普通知识问题 — PASS

回答先确认用户已经讲清的那一句：

## 6. 关键发现：1024 token 会把回答截断

第一次正式跑使用本地原配置 `max_tokens=1024`，结果：

| 场景 | 原始字数 | 结尾 |
| --- | ---: | --- |
| A | 440 | 停在「……和 cache 」 |
| B | 444 | 停在「- **未命中**」 |
| C | 591 | 停在「- 你的」 |
| C-only | 479 | 完整结束 |
| D | 1087 | 停在「……只是」 |

四个场景的结尾都在句子中间。把预算提高到 `4096` 后，五个场景全部以完整句子
结束，且供应商终态为 `finish_reason=stop`。原因是 `deepseek-flash` 的推理内容
也会消耗生成预算；1024 对中文长回答不够。

> 证据边界：本轮评测脚本已补上 `stream_chat_with_completion` 转发，因此正式产物
> 记录了 `finishReason` / `truncated`。1024 那一轮发生在补转发之前，只能从
> 「结尾在句子中间 + 字数明显偏短」推断截断，不能声称当时看到了 `length`。

结论：**本地 `.env` 已从 1024 调整为 4096**；如果继续用 1024，普通知识回答仍可能
被截断，且用户会收到不完整内容。

## 7. HistoryGuard 误判：否定式复述

本轮最有价值的负面发现不是「模型编造」，而是**校验器把正确的否认也当成断言**。

触发文本：

> 同时也不能反过来断言「你以前没有这个错误」，因为过去的信息没有呈现……

规则：

```python
_NO_HISTORY_DENIAL_RE = re.compile(
    r"你(以前|之前|过去|当时)[^。！？!?\n]{0,10}(没有|从未|从没|不曾)"
    r"[^。！？!?\n]{0,10}(错误|误解|问题|犯过|出现)"
    ...
)
```

它没有区分「你以前没有这个错误」和「不能断言你以前没有这个错误」。结果是：

1. 首答被误判，触发一次不必要的重生成；
2. 重生成仍被误判，最终走 fallback；
3. 用户拿到的是确定性文本，不是模型回答；
4. C-only 的模型调用从 1 次变成 2 次，首字延迟从约 5.5 s 变成约 11.2 s。

这是**保守但可观察的误报**：安全性没有受损（fallback 正确），但浪费了一次生成，
并掩盖了模型其实已经正确处理历史缺失的事实。建议后续把「不能 / 无法 / 不应
反过来断言」等否定框架纳入句子级判断，或对 `no_history_denial` 增加前文否定词
检查；本轮不修改生产校验器，先保留真实行为。

### A.rawAnswer

```text
本轮没有可用的上传资料，下面是通用知识。

## 直接回答

TLB 缓存的是**页表项（PTE）**，也就是一条条已经查好的「虚拟页号 → 物理页框号 + 权限位」的翻译结果，**不是页表本身，更不是整张页表**。

## 原来的推理在哪一步分叉

核心问题是：把「缓存页表的访问**结果**」听成了「缓存页表」。

页表是内存里的一个数据结构，多级结构的话本身可能有几 MB，并且每个进程一张。TLB 是 CPU 内部一个很小的部件，通常只有几十到上千个条目。容量差了几个数量级，它在物理上装不下页表。所以它只能做「小抄」这种用途：记住最近用过的那几条翻译。完整结构和缓存副本不是一个东西。

打个比方：页表是字典，TLB 是你贴在屏幕边上的便签，上面只抄了最近查过的那几个词。便签不是字典的副本；便签上没有的词，也不代表字典里没有。

| | 页表 | TLB |
|---|---|---|
| 存在哪 | 内存 | CPU 内部 |
| 内容 | 全部虚拟页的映射 | 最近用到的少数几条 PTE |
| 容量 | 覆盖整个地址空间 | 几十～上千条目 |
| 谁维护结构 | 操作系统建立/修改 | 硬件自动填充，OS 在切换进程等时机刷新 |

## 顺着这个区分，「TLB miss 就等于缺页」这一步也需要调整

这两件事处在不同层次：

- **TLB miss**：要用的翻译不在便签上。这时 CPU 需要重新查页表：x86 这类架构由硬件自动查询多级页表；另一些架构会触发一个专门的异常，由操作系统软件填充 TLB（具体由谁负责，不同架构不一样，这属于实现细节）。如果页表项有效，就把结果填入 TLB 再继续执行，**整个过程中不会发生缺页异常，程序完全不会察觉**。
- **缺页异常**：查到页表项后发现它无效、页面不在内存，或者权限不满足。这时才会陷入操作系统，由 OS 处理，再由它决定从哪读入页面或终止进程。

所以两者并不等价：TLB miss 是常见的高频事件，页表项有效时它只是一次较慢但无异常的内存访问；只有页表项本身有问题时，才会升级成操作系统处理的异常。反过来，TLB 命中也不代表一定安全：权限位也保存在 TLB 里，即使命中，也可能因为越权写入而触发保护性异常，同样交给 OS。

一句话概括：**TLB 缓存的是“翻译结果”，miss 只是“便签上没有，去翻字典”，翻出来的结果不对才是“字典里这一页有问题”**。
```

你对 TLB 缓存的是什么已经讲得很清楚了——缓存的是页表项（最近用过的那些条目），不是整张页表。这一点就不再展开了，重点放在它「怎么被用起来」上。

## 1. 它存在的理由：省掉一次访存
一次普通的内存访问，如果页表在内存里，要先读页表项拿到物理页号，再去读数据——等于一次访问变成两次。TLB 就是在 CPU 和页表之间加的一级快速查找结构，把「虚拟页号 → 物理页号」的换算做成近乎零代价。

## 2. 命中：纯硬件路径，操作系统完全不参与
地址翻译是 MMU 在每个访存上做的事。命中时，MMU 直接从 TLB 取出物理页号和权限位，拼出物理地址，继续访存。这一整套不需要任何软件介入。

## 3. 缺失：这里最容易混淆，要分清三件事

很多人会把「TLB 缺失」和「缺页」当成一回事，实际上是三个不同层级的问题：

| 发生了什么 | 谁发现 | 谁处理 |
|---|---|---|
| TLB 里没有这个映射，但页表里有 | 硬件（MMU） | 通常硬件自动页表遍历装入，或触发一个 TLB miss 异常交给操作系统软件处理——**取决于具体架构** |
| 页表里也没有这个映射（页面不在内存 / 从未建立） | 硬件检查 PTE 的有效位 | 触发缺页异常，**操作系统**处理：分配页框、从磁盘调页、更新页表 |
| 映射有，但当前权限不满足 | 硬件检查 PTE 权限位 | 触发访问异常（保护异常），**操作系统**处理（可能是报错，也可能是按需扩展栈之类） |

关键分界点：**TLB 缺失本身只是一个「缓存没查到」的事件，不必然是异常，更不必然是缺页。** 只有当顺着页表查下去、发现页表项本身无效时，才升级成缺页异常。而缺页异常的处理者是操作系统，不是 TLB、也不是页表自己会「去修好」。

至于 TLB 缺失后由硬件遍历页表还是陷入软件遍历，各架构做法不同——x86 这类是硬件页表遍历（page table walker），MIPS 等一些架构是软件填充。这一点我不打算给你一个统一的答案，得看具体架构。

## 4. 和进程切换的交互
不同进程的虚拟地址可能映射到不同物理页，所以切换页表时，旧进程的 TLB 条目不能继续生效。常见做法有两种：整表刷掉（简单但代价大），或者给每个条目打上地址空间标识（ASID / PCID），只让匹配当前标识的条目命中。具体怎么实现同样是架构相关。

## 5. 它在存储层次里的位置
TLB 管的是「地址翻译」这件事的缓存，数据缓存（L1/L2/LLC）管的是「数据本身」的缓存，两者是正交的两条路径，不要混成一级。至于 TLB 通常几路组相联、多少条目——这类参数各处理器差异很大，属于实现细节，我这里没有可靠依据给你具体数字。

如果你想把某一块往下挖，我建议从第 3 点那张表开始：TLB 缺失 → 页表遍历 → 缺页异常，这三步的边界是最容易讲错的地方。

在你这句基础上往下推，可以把 TLB 拆成三层来看：

**1. 一个 TLB 项里装的是什么**

一个 TLB 项通常由两部分组成：一部分是“键”，也就是虚拟页号（VPN）；另一部分是“值”，取自页表项的内容，比如物理页框号（PFN）、权限位、有效位。因此，TLB 可以理解成一个以 VPN 为索引的小表：查 TLB 就是在问“这个虚拟页最近翻译过没有，翻译结果是什么”。至于它内部采用全相联还是组相联，以及具体替换策略如何，这些属于实现细节，不同处理器并不相同，我无法替你确定。

**2. 一次地址翻译的顺序**

虚拟地址进入 MMU 后，大致经过这几个环节：

- 先查 TLB。命中时就直接拿到 PFN，与页内偏移拼成物理地址，**根本不用访问内存中的页表**。这正是 TLB 存在的意义：省掉每次访存都要多走一次内存的开销。
- 未命中时，就去内存里按页表逐级遍历（多级页表，或单级页表），找到对应的页表项，然后把它填入 TLB，再重试这次访问。
- 只有当遍历过程中发现页表项无效，或者页不在内存时，才产生缺页异常。

**3. 别把两个层级的事件混起来**

这是最容易混淆的一步：

- **TLB miss 只是“缓存没命中”**，它本身不是错误。补上它的是页表遍历：有的架构由硬件自动完成（hardware page table walker），有的架构会陷入操作系统，由软件填入，具体取决于架构，这一点我不能笼统替你确定。
- **缺页异常是“页表本身说不通”**，比如 PTE 无效、页被换出，或者权限不满足。这类异常由**操作系统**处理，不是 TLB 或页表结构自己处理。

所以“TLB 未命中”和“缺页”不是同一件事：前者是缓存问题，后者是映射问题。

再补一个常被忽略但很实际的点：TLB 里的内容必须和页表保持一致。进程切换、页表项被改写、页被换出时，旧的 TLB 项就成了过期映射，因此需要刷新 TLB，或者给表项打上地址空间标识（ASID/PCID 之类），以便区分不同进程的条目。具体采用哪种机制同样依架构而定。
